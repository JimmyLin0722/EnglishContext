# BUG-002 切換到句型庫頁在 4 倍 CPU 降速下超過 100ms

## 重現步驟

| 步 | 操作 |
| :--- | :--- |
| 1 | 以 Chrome 開啟 `dist/english-master-track.html`，DevTools Performance 設 CPU 4x slowdown（自動化：CDP `Emulation.setCPUThrottlingRate { rate: 4 }`） |
| 2 | 由導覽依序點「自訂器、抽認卡、Part 5、解碼器、句型庫、主控台」，再重複一輪 |
| 3 | 量測每次從點擊到下一次繪製完成的時間（自動化：`click()` 前後以 `performance.now()` 計時，等待 `requestAnimationFrame` + `setTimeout 0`） |

自動化：`tests/e2e/e2e-env.mjs` 的 TC-22-01；量測環境為本機無頭 Chrome（22 個邏輯核心的桌機，效能高於 PRD 指定的「中階筆電」）。

## 預期結果（引用 AC）

AC-22-01：「基準環境（中階筆電 + 最新 Chrome；另以 DevTools 4 倍 CPU 降速模擬手機，**兩種條件都要量測**）→ 點擊導覽切換頁面，量測 10 次 → 從點擊事件到新頁面完成繪製，每次 ≤ 100ms」。

## 實際結果

4 倍降速、連續 6 次重新載入的量測（單位 ms；第 1 輪含載入後暖機）：

| 頁面 | 6 次量測 | 最大 |
| :--- | :--- | :--- |
| 首次 句型庫 | 479、107、115、165、225、131 | 479 |
| 再次 句型庫 | 105、99、164、91、138、79 | 164 |
| 首次 自訂器 | 320、44、45、47、95、46 | 320 |
| 首次 解碼器 | 399、24、26、31、20、24 | 399 |
| 其他頁再次切換 | 全部 ≤ 41 | 41 |

驗收套件 TC-22-01 共執行 4 次，一般條件最大 68.9～73ms（皆通過）；4 倍降速每次都有不合格，且超標的都是切到句型庫（第 5 次）或再次切到抽認卡：

| 執行 | 4 倍降速 10 次（ms） | 最大 |
| :--- | :--- | :--- |
| 1 | 68.5、21.6、36.9、56.1、**275.4**、41.2、70.9、**110.5**、34.4、28.4 | 275.4 |
| 2（`npm run test:e2e`） | 61.6、61.4、36.1、48.6、**260.5**、31.1、71.6、**106.8**、23、30.6 | 260.5 |
| 3 | **138.3**、25.8、14.3、35.3、97.1、19.2、45.5、69.9、23.2、14.5 | 138.3 |

點擊處理函式本身只花 0～26ms，時間主要耗在句型庫一次繪製 100 張句型卡的樣式計算與版面配置；離開後再回到句型庫仍需重新繪製（79～164ms）。同一原因也可能影響 AC-16-01（同列 NFR-4）：另行探測時，4 倍降速下把搜尋字清空、清單由少數恢復為 100 則，3 輪中 2 輪出現 103～137ms；驗收套件 TC-16-01b 該輪最大 51.5ms（通過），屬偶發，請一併在 TC-M07 觀察。

## 可能原因（選填）

`src/app/views/phrasebank.js` 在切換頁面與篩選時，一次重建或顯示全部 100 個 `.pb-item`。可考慮：首次只繪製可視範圍附近的項目再分批補上、對 `.pb-item` 使用 `content-visibility: auto` 與 `contain-intrinsic-size`（`60-phrasebank.css`），或保留已建立的 DOM 只切換 `hidden`。修正後請以 4 倍降速重跑 `node tests/e2e/e2e-env.mjs` 確認 TC-22-01，並由人工 TC-M07 在基準環境複測。

註：首次切換到自訂器、解碼器的偏高數值只出現在載入後第 1 輪（暖機），其餘 5 輪皆 ≤ 95ms，不列入本缺陷；請人工 TC-M07 在基準環境一併觀察。

### 第 1 輪：PG 改寫單元測試斷言的判定

PG 把 `phrasebank.test.js` 的「不得出現 `setTimeout`」改為「計時器只能出現在 `scheduleIdle`／`cancelIdle`」。判定**符合** AC-16-01 與 architecture §7.6「每次 `input` 事件同步過濾，不做 debounce」的原意：

| 檢查 | 結果 |
| :--- | :--- |
| 程式路徑 | `input` → `setKeyword` → `apply(false)`，在事件處理內同步設定 `hidden`、筆數與「找不到」；`apply` 結尾的 `scheduleRest()` 只排入 content-visibility 標記與預設條件下的補卡片，不延後任何篩選結果 |
| 行為驗證 | TC-16-01c 每次都在 `dispatchEvent` 返回後立即讀取 DOM（尚未讓出主執行緒），可見則數 = 預期（4 次執行 × 10 筆，「結果不符或非同步」0 次） |
| 斷言強度 | 移除兩個函式本體後，仍禁止 `setTimeout`、`clearTimeout`、`debounce`、`requestAnimationFrame`，搜尋路徑若加入延遲仍會失敗 |

上述第 3 點是**同步但太慢**，屬效能問題（100ms），與「不得防抖」無關。

### 第 1 輪：可能原因與建議（選填）

| 項目 | 建議 |
| :--- | :--- |
| 首次按鍵（第 3 點） | 非預設條件時不要一次建立全部剩餘節點：只同步建立「符合條件」的節點，或只建立首屏所需的符合節點，其餘仍交給閒置分批；也可在 mount 時就建立全部 100 個節點（建立 DOM 的成本小），改用估計高度的 `contain-intrinsic-size` + `content-visibility: auto`，讓視窗外卡片跳過排版，不必延後建立 |
| 自訂器（第 2 點） | 用 Performance 錄製「開啟降速 → 重新載入 → 立即點自訂器」，確認時間是花在 customizer 的 show／繪製，還是載入後仍在進行的背景工作（例如 GC 或啟動後的閒置工作）佔用了主執行緒 |

驗證方式：`node tests/e2e/e2e-env.mjs` 執行至少 4 次，TC-22-01、TC-16-01b、TC-16-01c 每次都通過；診斷 `node tests/e2e/perf-phrasebank.mjs` 的「首次操作 key」每次 ≤ 100ms。原始紀錄：`tests/results/diag/bug-round1/`、`tests/results/diag/perf-phrasebank.json`。
