# BUG-007：本次載入第 1 次按麥克風，「準備中」約 110～131 ms 才出現（超過 AC-58-01 的 100 ms）

**範圍**：只有每次載入頁面後的**第 1 次**按麥克風（及離開單字卡頁再回來後的第 1 次，約 36～43 ms，未超過）。之後的按下約 1 ms。屬第 10 輪（1.3.1）新 AC；1.3.0 沒有「準備中」，無從比較，但同一段耗時在 1.3.0 也存在（按下後要等取得麥克風才有畫面變化）。

## 重現步驟

1. `node tests/e2e/e2e-stt-flow.mjs`（第 8 段 TC-58-01f），或手動：
2. 無頭 Chrome（或 Edge）1366×900，localStorage「STT 說明已讀」，開啟單字卡頁。
3. 以 init script 讓 `navigator.mediaDevices.getUserMedia` 回傳永遠擱置的 Promise（模擬權限詢問未回答；排除替身自己建立音訊的時間，只量產品）。
4. 頁面內執行：`t0 = performance.now(); btn.click(); t1 = performance.now();`，再等下一個 `requestAnimationFrame`。
5. 重複「重新載入 → 第 1 次按下」。

## 可能原因（選填）

`services/mic.js` 在 `acquire()` 內**同步**建立 `AudioContext`（檔內註解：「仍在使用者點擊處理中，符合自動播放政策」）。`speech-panel.js` 的 `beginAttempt()` 先 `setStatus("preparing")`，再同步呼叫 `acquireThenListen()` → `mic.acquire()`，所以「準備中」要等 `AudioContext` 建好後才畫出來。可能的方向（由 SD 判定）：先讓「準備中」畫出（例如等 1 個畫格）再取得麥克風；Chrome 的 user activation 在點按後數秒內有效，但是否仍符合自動播放政策需要實測。`services/mic.js` 不在 FE-92 paths，修正歸屬請 SD 決定。
