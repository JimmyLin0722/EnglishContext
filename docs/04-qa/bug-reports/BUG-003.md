# BUG-003 icon-512.png 最下方 1 列殘留來源圖的灰色外框

## 重現步驟

| 步 | 操作 |
| :--- | :--- |

| 2 | 解碼 PNG（RGB 8 位元），計算四邊各 1 列／欄像素的平均色，以及四角像素 |
| 3 | 自動化：`node tests/e2e/e2e-pwa.mjs` 的 TC-34-03a（`tests/e2e/lib/pwa-env.mjs` 的 `decodePng`）；放大檢視：四角各 48×48 放大 6 倍 |

## 預期結果（引用 AC）

AC-34-03：「圖示看不到來源圖的灰色外框與陰影，**四角無灰色或透明殘留**（Q-41 決議 A：裁掉灰邊與陰影、四角補滿藍色）」。契約 DP-4 (c)：「取自來源圖裁掉灰色外框與陰影後的藍色方塊，四角補滿藍色成滿版正方形」。

## 實際結果

`icon-512.png`（manifest `icons[1]`，`purpose: any`）最下方第 512 列整列為淺灰色，與上一列的藍色明顯不同；左下、右下兩角也是灰色：

| 位置 | 平均色（R,G,B） |
| :--- | :--- |
| 最下方 1 列（y = 511） | **(172, 186, 204)**（淺灰藍；512 個像素全部 B−R < 50） |
| 倒數第 2 列（y = 510） | (33, 100, 173)（藍） |
| 最上方 1 列 | (97, 190, 236)（藍） |
| 左下角、右下角像素 | **(182, 193, 208)**、**(181, 192, 207)**（灰） |
| 左上角、右上角像素 | (140, 195, 222)、(140, 194, 222) |

其他 3 張圖示比較（同一方法）：

| 檔案 | 最下方 1 列平均色 | 判讀 |
| :--- | :--- | :--- |
| `icon-192.png` | (77, 128, 185) | 比上一列 (16, 94, 180) 偏淡，縮小時混入灰邊，仍為藍色調 |
| `apple-touch-icon-180.png` | (73, 126, 185) | 同上 |
| `icon-maskable-512.png` | (26, 138, 238) | 正常（四周為補邊藍色） |

TC-34-03a 輸出摘錄：`icon-512.png：512×512、外圈 2px 非藍 516/4096、灰 4、四角 [[140,195,222],[140,194,222],[182,193,208],[181,192,207]]、各邊平均色 {"上緣":[97,190,236],"下緣":[172,186,204],...,"下緣上一列":[33,100,173]}`。

maskable 圖示的安全區檢查通過：白色文字與橘色對話框最遠距中心 203.8px，小於安全圓半徑 204.8px，圓外無白色、橘色像素（縮放 78% 屬已知事項 SD-FB-31，非本缺陷）。

## 影響

- 1px 灰線在 512 圖示上肉眼不易察覺，但 Windows 開始功能表大圖示、Android 啟動畫面（使用 512 圖示）放大時可能看到底部一條淺色線。
- 不影響安裝、離線、更新等功能；屬外觀，嚴重度 minor。

## 可能原因（選填）

`sources/pwa/README.md` 步驟 1 的裁切範圍 `crop((341, 342, 1707, 1708))`：下方邊界多含 1 列（或抗鋸齒過渡列）來源圖的灰色外框；四角 flood fill 只處理「與角落相連的非藍色」像素且以同列往內第一個藍色像素取代，最下方整列都是非藍色時沒有可取代的藍色。建議裁切下界內縮 1～2px（例 `1706`），或 flood fill 後對四邊各 1 列做檢查；重新產生 4 張 PNG 後 `npm run build`，BUILD_ID 會自動改變（AC-36-01 (c)）。

## 修正後驗證方式

`node tests/e2e/e2e-pwa.mjs` 的 TC-34-03a：四張圖示外圈 2px 非藍色比例 < 1%、無灰色像素、四角皆為藍色；另由人類在 TC-PWA-H1／H2 實機目視確認。
